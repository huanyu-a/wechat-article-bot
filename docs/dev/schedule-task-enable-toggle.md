# 定时任务的启动 / 停止

## 问题

定时任务原先只有「编辑弹窗里的一个勾选框」能改启用状态：想临时停掉一个每天跑的任务，
必须打开编辑、确认整张表单、再保存。任务卡片右上角虽然有「运行中 / 已停用」徽标，
但它是**只读的 div**，点了没有任何反应——看起来像开关，实际不是。

这带来两个实际后果：

1. 想停一个任务只能改表单，容易手滑改到别的字段；
2. 徽标写「运行中」但启用 ≠ 正在执行，停用中的任务在卡片上也无法直观区分「停止调度」与「这次失败了」。

## 方案

### 接口：只带一个字段

```
PUT /api/tasks/{id}/enabled
{ "enabled": true | false }
```

返回更新后的 `TaskView`。

**为什么不复用 `PUT /api/tasks/{id}`**：它要求整份 `TaskRequest`，其中 `name`、`cronExpression`、
`aiPrompt` 都是 `@NotBlank`。让「点一下开关」提交整张表单有两个坑：少一个字段被拒；
更糟的是前端必须先读再整体回写，**读漏一个字段就会把它静默清空**。启停是一个字段的操作，
就只接受一个字段。

**为什么用 PUT**：它是幂等的状态设置（连点两次「停止」结果一样），与 `POST /{id}/run`
（每次调用都产生一条新运行记录，天然非幂等）区分开。

### 服务层：`ScheduleTaskService.setEnabled(id, enabled)`

- 只改 `enabled`，其它字段一律不碰；
- 启用前调用 `requireFutureFire(task)`，与创建/编辑共用同一段校验；
- 写库后调用 `quartz.schedule(task)`：停用时它删掉 Quartz Job 并把 `next_run_at` 置空。

最后一点是这次要修的实际缺陷的延伸：**任务不会跑了，界面却还显示一个未来的「下次执行」**，
用户会一直等一个永远不会发生的运行。

### 「已过期的计划」必须拒绝启用

一个 `cron` 指向过去（例如 `0 0 9 1 1 ? 2020`）的任务，停用后再启用如果直接注册进 Quartz，
它永远不会触发，用户却看到绿灯。因此启用路径必须重新算一次「还有没有未来触发时间」，
没有就报错并且**不改状态**。

### 前端

任务卡片右上角的徽标改成真正的按钮：

- 文案 `已启用 / 已停止`（原来的「运行中」会让人以为正在执行）；
- 点击即切换，请求期间显示「切换中…」并禁用，避免连点发出两个相反请求；
- `aria-pressed` 反映状态，`title` 提示点击会发生什么；
- **不做乐观更新**：切换的是「调度是否生效」，本地先翻转而服务端拒绝时会短暂显示错误状态，
  这类状态宁可多等一次请求，也不能对用户撒谎。
- 成功后在提示条里给出结果，启动时附带算出的下次执行时间。

### 助手侧

`set_schedule_task_enabled` 工具原先「读全量 → 拼 TaskRequest → 整体回写」，
现在直接调用同一个 `setEnabled`，UI 与助手共用一条写路径。

## 验收

`ScheduleTaskEnabledApiTests`，6 项。每个用例都同时断言**接口返回、库里的 `ENABLED`、
Quartz 里 Job 是否存在**——这类开关最容易只改数据库而调度器照跑：

| 用例 | 断言 |
| --- | --- |
| 停止 | 接口 `enabled=false`、`nextRunAt` 消失；库里 false；**Quartz Job 不存在**；`next_run_at` 为空 |
| 重新启动 | 库里 true；**Job 重新出现**；`next_run_at` 重新算出 |
| 停止不动其它字段 | cron / 时区 / aiPrompt / outputMode 原样 |
| 过期计划启用 | 400，且状态保持不变 |
| 缺 `enabled` 字段 | 400（不是 500） |
| 任务不存在 | 400 |

手工验收（smoke 库，端口 8082）：创建后 `nextRunAt=2026-11-12 09:00:00` → 停止后返回空 →
再启动又算出同一时间。
