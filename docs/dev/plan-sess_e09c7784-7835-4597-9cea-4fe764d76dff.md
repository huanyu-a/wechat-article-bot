# 定时任务可靠性 + 效率优化 + 模型档案故障切换（一轮全做完）

已确认口径：**付费 Tier A 主用 + 免费兜底**；**一轮全做完**；工具治理取**去重 + 循环检测 + 预算提示**。

## 一、关键发现（决定了方案的形状）

1. **"按智能体分配模型"其实已经做好了，只是没人用。** `AGENT_DEFINITION.LLM_PROFILE_ID` 字段、`AgentFactory.createModel` 的解析链（绑定档案 → 默认档案 → `llm_config`）、以及前端 `AgentsView.vue` 的下拉都已就绪，但 `AgentSeeder` 种内置智能体时**没有写这个字段**，所以 7 个内置智能体全部落在默认档案上。这轮主要是"把它用起来"。
2. **故障切换能力完全不存在。** `AgentInvoker` 重试时复用同一个 `AgentClient`，而 `AgentClient` 在 `setModel` 时就绑死了一个模型；`isPermanent` 里 `model_not_found`/`no available channel`/`invalid_api_key` 这些**恰好是换模型能治好**的错误，被归为"永久不重试"。历史事故里 `agnes-3.0-flash` 被网关下线后的处置办法是**手工改库**。
3. **`temperature`/`maxTokens` 是死字段**：agent4j 2.3.3 的 `LLMModel.create` 只收 4 个参数，这两个覆盖项当前不生效（`AgentFactory.warnIfOverridden` 已在 debug 日志里承认）。方案不会依赖它们。
4. **效率的最大杠杆是模型速度**：当前 hy4-preview 23.5 tok/s，deepseek-flash 445 tok/s（19 倍），glm-5.3-flash 153 tok/s（6.5 倍）。上一轮 SINGLE 成功跑了 554 秒、COORDINATOR 1801 秒——其中相当大比例是纯生成等待。
5. **一次停滞要白等一整个超时**：SINGLE 900s、COORDINATOR 1800s。`StageTimeout` 是**墙钟**超时，不是"多久没动静"检测——模型卡住时会一直等到超时才被判死，这段时间完全浪费。
6. **没有任何循环检测**：模型重复 `search_web` 会被当成 40 次正常调用一路烧到预算上限（run#46/#62/#85/#89 都是这个形态）。`ToolMutationDeduplicator` 只覆盖 `generate_image`/`import_web_image`/`edit_image`，**不覆盖只读检索**。
7. **封面归属校验只在 SINGLE 链路**（`ArticleAiService:574-578`）。PIPELINE / COORDINATOR 产出的文章可以带别的公众号的封面素材。
8. **`MAX_SCHEDULED_TOOL_CALLS = 40` 是硬编码常量**（`ArticleAiService:64`），是唯一不受 `app.schedule.tool-calls.*` 配置约束的预算。
9. 遗留的 5 组同名字段声明冲突里，**`sourceUrl` 已造成真实收窄**：`Asset.java` 声明 2000，但 `ASSET.SOURCE_URL` 实际是 `varchar(1000)`。

## 三、Phase 1：模型档案故障切换（核心新功能）

### 1.1 档案链解析

在 `LlmProfileService` 新增 `failoverChain(LlmProfile bound)`，返回有序候选（去重、跳过未启用/无 key）：

```
① 智能体绑定的档案（该智能体的最优选择）
② 默认档案（is_default）
③ 兜底档案（is_fallback，见 Phase 2）
④ 其余已启用档案（按 id 升序）
```

链长上限 **3 次切换**（可配），避免把时间烧在遍历档案上。

### 1.2 装配层：一次建好候选 AgentClient

`AgentFactory` 新增 `buildCandidates(definition, skillContext, resolver)` → `List<AgentClient>`。
候选之间**只差模型**，工具实例与工作区完全共享（工具无模型状态，多建几个 client 是廉价且安全的）。

`ScheduledAgentFactory` 同步新增 `buildCandidates(...)`，沿用现有 `resolveTools` 与 `ToolMutationDeduplicator` 共享语义。

### 1.3 执行层：`AgentInvoker` 支持切换

`AgentRunner` 新增 `runWithCandidates(...)`，**带默认实现**（退化为只用第一个候选），因此现有实现与单测零改动。

`AgentInvoker` 的循环改为（在现有瞬时/停滞重试之上叠加）：

```
本次尝试零工具调用 且 是"模型级错误" 且 还有候选
  → 切到下一个候选，重建会话，继续
```

**"模型级错误"是 `isPermanent` 的严格子集**（只有换模型才可能治好的那几类）：
`model_not_found`、`no available channel`、`invalid_api_key`、`401`、`403`、`404`、`402`（该渠道额度耗尽）。

**明确不触发切换的**：
- `451`/`content_filter`（内容审查，换模型结果一样）
- `429`/`concurrent limit`（**账号级并发**，同一网关换模型无效）——仍走原有同模型退避重试
- 任何 `toolCalls > 0` 的情况（可能已生图/落库，换模型会重复计费）

**停滞也切换**：`StageTimeoutException` 且零工具调用时，那唯一一次停滞重试**直接换下一个候选**——模型卡死换模型比原地重试更对症，也更省时间。

### 1.4 可观测性（必须有，否则线上无法归因）

- 执行日志写入：`模型档案不可用（原因），切换 A → B（第 N 次）`
- `TaskWorkspace` 记录本次运行**实际使用过的档案链**，落入 `stages_summary`
- 运行终态消息在发生过切换时追加提示（走既有 warnings 通道）

### 1.5 编辑器链路（可选，默认包含）

编辑器走的是 `StageTimeout.await` 直连、**完全没有重试**。给它加同样的"模型级错误 → 换候选"（约 15 行）。会改变交互行为，若你想保守可单独去掉。

## 五、Phase 3：效率优化

1. **停滞改为"无进展检测"（收益最大的一项）**：`StageTimeout` 增加"距上次有效事件超过 N 秒即中止"（`app.schedule.retry.inactivity-seconds`，默认 180），硬超时仍作为外层兜底。SINGLE 的一次卡死从**白等 900s** 降到约 180s，且立刻触发换模型。
2. **调研简报注入前截断**：`researchNotes` 是 append-only 无上限，而 `writingCommand` 每轮返工都把全文重发。加长度上限（默认 12000 字）+ 截断提示，避免返工轮次上 token 成本二次增长。
3. **手动触发改用专用线程池**：`TaskExecutionService.start` 现在跑在公共 `ForkJoinPool` 上，一批手动触发会与其他并行工作互相饿死。复用已有的 `task-run-progress` 那套专用池做法。
4. **`MAX_SCHEDULED_TOOL_CALLS` 硬编码 40 → 走 `ToolCallBudget`**，与其他链路一致（这是配置一致性问题，顺带修）。
5. **技能提示只组装一次**：`resolveLayoutEngine` 与 `ScheduledAgentFactory.build` 现在各组装一遍，复用 `preAssembled`（`AgentFactory` 已支持该参数，只是调用方没传）。

> **不做**：PIPELINE 阶段并行化。看起来能省时间，但 `InFlightGate` 是**运行级**名额（一次运行只占一个），并行阶段会打破"一次运行一个在飞请求"的建模，风险远大于收益。模型提速（Phase 2）已经把这条收益覆盖掉了。

## 六、Phase 4：工具治理

1. **只读工具去重（新增 `ReadToolCache`）**：`search_web` / `browse_webpage` / `search_web_images` / `list_image_assets` 同参数重复调用时**不重复执行**，直接返回首次结果并附：
   `{"cached": true, "note": "同参数结果已在本次运行中获取过"}`。
   **仍然计入预算**（保住硬上限），但省掉一次真实网络往返与上游延迟。
2. **循环检测**：同一工具+同参数的重复次数超过阈值（默认 2）时，在工具结果里注入**可执行的收手指令**（而不是干巴巴的报错）：
   `你已用相同参数调用 search_web 3 次且结果相同，继续重复不会带来新信息。请立即用收尾工具提交已有成果。`
   连续"无任何新工具/新参数"达更高阈值（默认 6）时**主动中止**该会话并给出明确原因。
   > 依据：`known-issues-handoff.md` 记录过模型读到"已中止"后仍连调 7 次工具——所以提示必须是**可执行的下一步**。
3. **预算提示**：剩余额度 ≤ 5 时，每个工具结果追加 `本次会话剩余工具调用额度：N 次，请优先提交成果`。让模型自己安排收尾，而不是靠事后拒绝。
4. **参数格式错**（`submit_review - Failed to parse tool param JSON`）：在 `AgentProtocols.REVIEW` 里补一个**完整 JSON 示例**（现有协议只列了字段名），并把这这类失败单独计数，便于观察是否下降。
5. **封面归属校验上提到 `TaskExecutionService`**：三链路统一校验，修掉 PIPELINE/COORDINATOR 的缺口。
